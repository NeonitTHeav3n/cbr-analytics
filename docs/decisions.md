# Решения и компромиссы

Короткие записи «почему так» — чтобы на собеседовании не вспоминать задним числом,
и чтобы самому через полгода не смотреть на код как на чужой.

## 1. DuckDB как основное хранилище, Postgres — как опция

**Решение:** по умолчанию `data/cbr.duckdb`, Postgres поднимается через `docker compose` и включается
переменной `CBR_ENGINE=postgres`.

**Почему:** главное свойство пет-проекта — он должен запускаться. `git clone && make all` работает
без Docker, без паролей и без сервера. Данных здесь ~13 тысяч строк: Postgres как СУБД ничего не даёт,
кроме лишнего шага в quickstart. При этом SQL написан в переносимом подмножестве, и на Postgres есть
отдельный путь (`_adapt_for_postgres` разворачивает `CREATE OR REPLACE TABLE` в `DROP` + `CREATE`),
так что у проекта остаётся путь к настоящему BI — Metabase.

**Цена:** одна и та же витрина проверяется тестами только на DuckDB; различия диалектов ловятся глазами.
Заменяется переходом на dbt, если витрин станет много.

## 2. Сырые данные не перезаписываем

**Решение:** ответы ЦБ лежат в `data/raw/...` партициями «валюта / период», повторный запуск читает кэш
(`--force` — чтобы перекачать).

**Почему:** это bronze-слой и одновременно защита от rate limit. Если парсер сломается, данные
не надо качать заново, и любую ошибку можно воспроизвести на том же файле. Побочный плюс: `make build`
работает секунды и не требует сети, что делает его пригодным для CI.

## 3. Один запрос = один год

**Решение:** история тянется кусками по 1 году (`chunk_years: 1`).

**Почему:** CBR отдаёт `XML_dynamic.asp` за весь диапазон сразу, но один сетевой сбой в конце
11-летней истории обнулял бы всю загрузку. С чанками падение стоит одного года, остальное — в кэше.

## 4. Календарь с forward fill для курсов

**Решение:** `int_currency_daily` строит непрерывный календарь и протягивает последний известный курс
на выходные и праздники.

**Почему:** без этого нельзя честно сравнивать «вклад за 365 дней» и «валюта за 365 дней»: курс
на 365-й день мог не публиковаться. Альтернатива — считать горизонты в торговых днях, но тогда
депозит пришлось бы считать по тем же дням, и цифры перестают быть похожими на банковскую выписку.

**Но:** для волатильности forward fill вреден (см. п. 5).

## 5. Волатильность — только по дням публикации, аннуализация √252

**Решение:** `int_fx_returns` берёт даты, где курс реально публиковался, и умножает σ на √252.

**Почему:** если считать по календарю с протянутыми выходными, ~1/7 наблюдений имеют нулевую
доходность и σ систематически занижается (примерно на 13%). Это ошибка, которую легко не заметить:
график выглядит правдоподобно, а число неверное.

## 6. Вклад = `exp(sum(ln(1 + r/365)))`, а не `r × дней/365`

**Решение:** накопленный индекс считается через сумму логарифмов дневных множителей.

**Почему:** ключевая ставка менялась 30+ раз за период; «средняя ставка × срок» игнорирует порядок
изменений и компаундирование. Лог-сумма даёт точное произведение множителей и одновременно удобна
для расчёта доходности между двумя произвольными датами: `index(d2) / index(d1)`.

**Проверка:** интеграционный тест сверяет результат с аналитической формулой `exp(0.10) − 1`
для постоянной ставки 10%.

## 7. Доля побед + медиана, а не средняя доходность

**Решение:** в `mart_headline` считаются `deposit_win_share`, медиана и p10/p90 разницы.

**Почему:** средняя разница скрывает распределение. Пользователю важно не «в среднем вклад лучше
на 9,8 п.п.», а «в каждом третьем случае валюта всё равно выигрывала, и проигрыш доходил до −14,6 п.п.».
p10/p90 показывают риск, который средняя прячет.

## 8. Свой SVG вместо Plotly/Altair

**Решение:** `report/charts.py` рисует SVG вручную, дашборд — один HTML-файл без CDN.

**Почему:** отчёт должен открываться офлайн, не зависеть от версии CDN и весить сотню килобайт.
Плюс это честный сигнал: человек, который рисует SVG руками, понимает, что такое шкалы и оси,
а не только `px.line()`.

**Цена:** нет интерактивности и зума. Для BI-сценария в проекте предусмотрен Metabase.

## 9. Проверки качества как часть пайплайна, а не отдельный ноутбук

**Решение:** `transform/quality.py` бросает `QualityError`, и пайплайн останавливается.

**Почему:** данные, прошедшие в витрину без проверки, дороже отсутствия данных: их начинают
использовать в решениях. Проверки дешёвые (6 SQL-запросов на витринах) и ловят самые частые поломки:
пустой ответ API, дубли, отрицательный курс, скачок в 10 раз.

## 10. Выводы генерируются из данных

**Решение:** `findings()` в `dashboard.py` собирает текст из витрин, а не из головы автора.

**Почему:** цифры в README не расходятся с цифрами в дашборде после обновления данных.
Еженедельный workflow пересобирает отчёт — и текст вместе с ним.
